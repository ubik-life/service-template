# platform-landing.skill — Лендинг платформы + парный get-started

## Назначение

Скилл для слабой модели (Haiku/Sonnet). На вход — concept-репо платформы
(новый или с историческим README). На выход — пара документов:

1. `README.md` — лендинг (витрина для одного читателя, ≤ 120 строк).
2. `docs/get-started.md` — вложенная пошаговая страница (подключение до
   видимого результата).

Метод: детерминированный конвейер из 5 pass'ов. Никаких суждений —
каждый шаг это либо `read → classify → fill slot`, либо `STOP, ask human`.

## Зона ответственности

DO:
- Писать **только под одного читателя** — инженера-потребителя.
- Применять жёсткие лимиты (число слов, число буллетов, число строк).
- При рефакторе — **разводить найденный контент по правильным файлам**,
  не выкидывать.
- Останавливаться по STOP-правилам, не выдумывать недостающее.

DON'T:
- Класть на лендинг архитектуру, манифест, длинный quickstart,
  troubleshooting, детальный roadmap (антиконтент-таблица — ниже).
- Принимать решения о манифесте, ценностях, формулировке tagline
  без человека.
- Удалять контент из старого README. Перенесённое — должно где-то
  оказаться (см. таблицу маршрутизации в Pass 3).
- Писать структуру для `docs/architecture.md` и `docs/manifesto.md` —
  только сложить туда сырьё с пометками `<!-- TBD: structure -->`.
  Структурирование этих файлов — задача другого скилла.

## Кто читатель и какой у него job

**Один читатель: инженер-потребитель** — разработчик из другой команды,
который рассматривает платформу для интеграции.

| Поверхность | Глубина | Job | Бюджет внимания |
|---|---|---|---|
| `README.md` (лендинг) | shallow | Решить «годится ли мне», сделать первый шаг | 60 секунд |
| `docs/get-started.md` (вложенная) | deep | Дойти до видимого результата своими руками | 30 минут |

Менеджер, стейкхолдер, мейнтейнер сюда **не входят**. Если найденный
контент адресован им — Pass 3 разводит его по другим файлам.

## Антиконтент-таблица (что лендинг **не** содержит)

| Найдено в кандидате на лендинг | Класс | Куда едет в Pass 3 |
|---|---|---|
| Архитектурная диаграмма, схема компонентов с потоками | `architecture` | `docs/architecture.md` |
| Принципы, манифест, «как мы работаем» | `manifesto` | `docs/manifesto.md` |
| Quickstart > 10 строк, пошаговая инструкция | `get-started` | `docs/get-started.md` |
| «Если не работает — попробуйте…», troubleshooting | `get-started` | `docs/get-started.md` |
| Roadmap длиннее одного абзаца | `roadmap` | `docs/roadmap.md` |
| Список интеграций с деталями каждой | `architecture` | `docs/architecture.md` |
| Сравнение с конкурентами длиннее 3 строк | `marketing` | `docs/_refactor-notes-<date>.md` (на ревью) |
| ADR, обоснование выбора технологий | `architecture` | `docs/architecture.md` |

## Жёсткие лимиты (grep-проверяемые)

| Элемент лендинга | Лимит |
|---|---|
| Tagline (one-liner после заголовка) | ≤ 12 слов |
| Why-секция | ровно 3 буллета |
| Hello-world блок кода | ≤ 10 строк |
| Use case'ы в секции «Что можно собрать» | ровно 3, по одной строке каждый |
| «Где сейчас» | ровно 1 строка |
| «Вопросы» | ровно 1 строка |
| Весь лендинг | ≤ 120 строк (`wc -l README.md`) |
| Один шаг пути A/B в get-started | ровно 1 команда + ожидаемый вывод |

Если лимит нарушен — обрезать или вынести в `docs/_refactor-notes-<date>.md`.

## STOP-правила (когда модель обязана остановиться)

Модель **не выдумывает** недостающие куски. При любом из условий ниже —
остановиться, оставить `<<HUMAN_NEEDED: причина>>` в соответствующем
слоте, добавить запись в `docs/_refactor-notes-<date>.md`, продолжить
следующий слот.

1. Tagline не выводится из старого README (нет ни одного оборота «X для Y»
   или «делает Z»).
2. Why-буллетов в исходниках меньше 3 и нельзя извлечь из READMEs дочерних
   сервисов.
3. Hello-world пример не существует ни в одном из READMEs платформы.
4. Hello-world существует, но содержит `<TODO>` / `<...>` /
   «замените на ваш …» — это значит, что пример нерабочий.
5. Фрагмент в Pass 0 не классифицируется ни в один из 5 классов
   (`landing` / `get-started` / `architecture` / `manifesto` / `roadmap`).
6. Component map: дочерних компонентов 0 или 1. Лендинг платформы
   из одного сервиса — не платформа. Спросить, является ли это
   действительно платформенным продуктом.

## Pass 0 — Inventory

**Цель:** разобрать существующий README на фрагменты и классифицировать.

**Вход:**
- `README.md` концепт-репо (если есть).
- READMEs всех дочерних репозиториев платформы (один уровень).

**Действие:**

1. Разбить старый `README.md` на фрагменты по заголовкам уровня `##`
   (или по визуальным разделителям, если заголовков нет).
2. Для каждого фрагмента — присвоить **один** класс из списка:

   | Класс | Признак (триггерные слова) |
   |---|---|
   | `landing` | «что это», «зачем», «преимущества», «features», hero |
   | `get-started` | команды установки, шаги, «1. ... 2. ... 3. ...», `install`, `run` |
   | `architecture` | «компоненты», «диаграмма», «слои», «модули», ASCII-схема с `→` или `│` |
   | `manifesto` | «принцип», «правило», «никогда», «всегда», «мы верим», «values» |
   | `roadmap` | «план», «следующий шаг», «Q1 2026», «milestone», «coming soon» |
   | `marketing` | сравнение с конкурентами, цитаты пользователей |

3. Записать результат в `docs/_refactor-notes-<date>.md` (создать файл,
   если его нет) в формате:

   ```markdown
   ## Inventory <YYYY-MM-DD>

   | Фрагмент (заголовок или первые 60 символов) | Класс | Куда едет |
   |---|---|---|
   | "## Что это"                                  | landing  | README.md |
   | "## Установка через docker-compose"           | get-started | docs/get-started.md |
   | "## Архитектура. Компоненты:"                 | architecture | docs/architecture.md |
   | ...                                            | ...      | ... |
   ```

**STOP-условия Pass 0:**
- Фрагмент не классифицируется → STOP, оставить с классом `?`, продолжить.
- README пустой и нет дочерних READMEs → STOP, сообщить оператору.

**Выход Pass 0:** заполненная таблица в `docs/_refactor-notes-<date>.md`.

## Pass 1 — Landing draft

**Цель:** собрать `README.md` из фрагментов класса `landing` +
заполнить недостающие слоты.

**Вход:**
- Фрагменты класса `landing` из Pass 0.
- READMEs дочерних сервисов (для составления Component Map).
- Шаблон `templates/landing-README.md.tmpl`.

**Действие:**

1. Скопировать `templates/landing-README.md.tmpl` в `README.md`
   (перезаписать, оригинал уже в git-истории).
2. Заполнить слоты в порядке появления в шаблоне:

   | Слот | Источник | Если нет |
   |---|---|---|
   | `<<SLOT_NAME>>` | название платформы (из старого README h1 / из имени org) | STOP |
   | `<<SLOT_TAGLINE>>` | первый абзац старого README, обрезанный до 12 слов | STOP 1 |
   | `<<SLOT_STATUS_BADGE>>` | строка с shields.io-бейджем, если найдена | оставить пустым |
   | `<<SLOT_WHY_BULLET_N>>` (×3) | 3 коротких фразы из `landing`-фрагментов | STOP 2 |
   | `<<SLOT_HELLO_WORLD_LANG>>` | язык первого кодового блока с командами | STOP 3 |
   | `<<SLOT_HELLO_WORLD_BODY>>` | тело этого блока, обрезано до 10 строк | STOP 3/4 |
   | `<<SLOT_USE_CASE_N>>` (×3) | 3 коротких use case'а из тех же фрагментов | `<<HUMAN_NEEDED: 3 use case'а>>` |
   | `<<SLOT_COMPONENT_ROWS>>` | по строке на каждый дочерний репо, через `templates/component-row.md.tmpl` | STOP 6 |
   | `<<SLOT_CURRENT_STEP_ONE_LINE>>` | строка из `CLAUDE.md` концепт-репо «Следующий шаг», обрезанная до 1 фразы | `<<HUMAN_NEEDED: текущий шаг>>` |
   | `<<SLOT_HELP_ONE_LINE>>` | одна строка с issue-tracker / discussions / contact | оставить пустым |

   «STOP N» — соответствующее правило из секции STOP-правил.

3. Применить лимиты (предыдущая секция). Если лимит превышен — обрезать
   до лимита, излишек положить в `docs/_refactor-notes-<date>.md`
   секцию `## Overflow Pass 1`.

4. Прогнать grep-проверки:

   ```bash
   # Tagline ≤ 12 слов
   awk '/^> / && !done {print NF; done=1}' README.md
   # должно быть ≤ 12

   # Why ровно 3 буллета (между ## Зачем и следующим ##)
   awk '/^## Зачем/,/^## /' README.md | grep -c '^- '
   # должно быть = 3

   # Всего ≤ 120 строк
   wc -l README.md
   # должно быть ≤ 120
   ```

**Выход Pass 1:** `README.md` с заполненными слотами и/или
`<<HUMAN_NEEDED: ...>>` маркерами.

## Pass 2 — Get-started draft

**Цель:** собрать `docs/get-started.md` из фрагментов класса
`get-started`.

**Вход:**
- Фрагменты класса `get-started` из Pass 0.
- Шаблон `templates/get-started.md.tmpl`.

**Действие:**

1. Скопировать `templates/get-started.md.tmpl` в `docs/get-started.md`
   (создать директорию `docs/`, если её нет).
2. Найти в `get-started`-фрагментах **две группы шагов**:
   - команды локального запуска (docker-compose / make / `go run`) →
     Путь A;
   - команды подключения к внешнему API/сервису платформы (curl с URL,
     `kubectl apply`, `terraform apply`) → Путь B.

   Если ни одной из групп нет — пометить путь как `<<HUMAN_NEEDED: путь N
   отсутствует>>` и продолжить.

3. Заполнить слоты:

   | Слот | Источник |
   |---|---|
   | `<<SLOT_INTRO_ONE_PARAGRAPH>>` | первая фраза из старого quickstart или 1-абзац-описание задачи |
   | `<<SLOT_PREREQ_N>>` (×3) | requirements из старого README (Docker, Go, версии) |
   | `<<SLOT_PATH_A_STEP_N>>` (×3) | первые 3 команды локального запуска |
   | `<<SLOT_PATH_A_STEP_N_CMD>>` | сама команда в `<code>` |
   | `<<SLOT_PATH_A_STEP_N_OUT>>` | ожидаемый вывод, если есть в исходнике; иначе `<<HUMAN_NEEDED>>` |
   | `<<SLOT_PATH_A_VERIFICATION>>` | curl/команда проверки + ожидаемый ответ |
   | `<<SLOT_PATH_B_*>>` | аналогично для подключения к существующей платформе |
   | `<<SLOT_ISSUE_N_*>>` (×3) | из секции «troubleshooting» / «known issues» старого README |
   | `<<SLOT_NEXT_STEP_N>>` (×3) | 3 ссылки на дочерние сервисы или ADR |

4. Применить правило **«один шаг — одна команда + один ожидаемый вывод»**.
   Если шаг содержит несколько команд — разрезать.
   Если шагов после разрезания > 30 — оставить только первые 10
   в Пути A, остальное положить в `docs/_refactor-notes-<date>.md`
   секцию `## Overflow Pass 2 (excess steps)`.

**STOP-условия Pass 2:**
- Ни одной команды запуска ни в README, ни в дочерних READMEs → STOP 3.

**Выход Pass 2:** `docs/get-started.md` с заполненными слотами.

## Pass 3 — Routing maintainer content

**Цель:** перенести фрагменты классов `architecture`, `manifesto`,
`roadmap` в правильные файлы.

**Действие:** для каждого фрагмента из Pass 0:

| Класс | Целевой файл | Что делать |
|---|---|---|
| `architecture` | `docs/architecture.md` | Создать файл, если нет. **Append** фрагмент дословно. В начале файла — пометка `<!-- TBD: structure (см. будущий maintainer-docs skill) -->` |
| `manifesto` | `docs/manifesto.md` | То же |
| `roadmap` | `docs/roadmap.md` | То же |
| `marketing` | `docs/_refactor-notes-<date>.md`, секция `## Marketing (на ревью)` | Дословно |
| `?` (не классифицирован) | `docs/_refactor-notes-<date>.md`, секция `## Unclassified` | Дословно + `STOP, ask human` |

**Правило сохранности.** Ни один фрагмент исходного `README.md`
не должен исчезнуть без явной записи о его судьбе в
`docs/_refactor-notes-<date>.md`. После Pass 3 — `grep` проверкой:

```bash
# Список всех заголовков ## из git-версии README до рефакторинга
git show HEAD:README.md | grep -E '^## ' > /tmp/old-headings.txt

# Каждый старый заголовок должен встретиться в одном из файлов
for h in $(cat /tmp/old-headings.txt | sed 's/^## //'); do
  grep -rln "$h" README.md docs/ || echo "LOST: $h"
done
```

Если хоть одна строка `LOST:` — STOP, сообщить оператору.

**Запрет.** Не структурировать `docs/architecture.md` и `docs/manifesto.md` —
это задача другого скилла (maintainer-docs, ещё не существует). Здесь
только складываем сырьё с пометкой.

**Выход Pass 3:** файлы `docs/architecture.md`, `docs/manifesto.md`
(если был соответствующий контент), обновлённый
`docs/_refactor-notes-<date>.md`.

## Pass 4 — Verify & link

**Цель:** проверить, что лендинг и get-started склеены, ничего не
потеряно, человеку понятно, где ему нужно решить недостающее.

**Чек-лист (каждая строка — yes/no, без суждений):**

1. **Лимиты.**
   - [ ] `wc -l README.md` ≤ 120.
   - [ ] Tagline ≤ 12 слов.
   - [ ] Why ровно 3 буллета.
   - [ ] Hello-world ≤ 10 строк.
   - [ ] Use case'ов ровно 3.

2. **Связь landing ↔ get-started.**
   - [ ] В `README.md` есть строка `→ **[Подключиться шаг за шагом](docs/get-started.md)**`.
   - [ ] Файл `docs/get-started.md` существует.
   - [ ] У `docs/get-started.md` есть хотя бы один из путей (A или B)
         без `<<HUMAN_NEEDED>>` маркеров в шагах.

3. **Component map.**
   - [ ] В таблице `## Из чего состоит` ≥ 2 строки.
   - [ ] Каждая ссылка в таблице резолвится (`curl -sI` возвращает 200
         для URL или путь существует для относительной ссылки).

4. **Маршрутизация мейнтейнер-контента.**
   - [ ] Если в Pass 0 был класс `architecture` — `docs/architecture.md`
         существует и содержит `<!-- TBD: structure -->`.
   - [ ] То же для `manifesto`, `roadmap`.

5. **Сохранность.**
   - [ ] Grep-проверка из Pass 3 не вернула ни одного `LOST:`.

6. **Маркеры для человека.**
   - [ ] Все `<<HUMAN_NEEDED: ...>>` собраны в начало
         `docs/_refactor-notes-<date>.md`, секция `## Что нужно от человека`,
         с указанием файла и строки.

7. **Антиконтент.**
   - [ ] В `README.md` нет ASCII-диаграммы со стрелками `→`, `│`, `├─`
         (если есть — это `architecture`, должно было уехать в Pass 3).
   - [ ] В `README.md` нет слов «принцип», «манифест», «мы верим»
         (если есть — это `manifesto`, должно было уехать).
   - [ ] В `README.md` нет блоков кода длиннее 10 строк.

   ```bash
   # Проверка диаграмм
   grep -nE '[│├└─→]' README.md && echo "ARCH LEAK"
   # Проверка манифеста
   grep -niE 'принцип|манифест|мы верим|values' README.md && echo "MANIFESTO LEAK"
   # Проверка длинных блоков кода
   awk '/^```/{c++; if(c%2==1){s=NR} else if(NR-s>11){print "CODE BLOCK TOO LONG at "s}}' README.md
   ```

8. **Финал.** Записать в `docs/_refactor-notes-<date>.md` блок:

   ```markdown
   ## Pass 4 — Verify (<YYYY-MM-DD>)

   - [x] Все 7 категорий чек-листа пройдены.
   - Файлы изменены: README.md, docs/get-started.md, docs/architecture.md, ...
   - Маркеров <<HUMAN_NEEDED>>: N (см. секцию выше).
   - Ожидается ревью оператора.
   ```

**Выход Pass 4:** готовый pull request с:
- новым `README.md`,
- новым `docs/get-started.md`,
- роутингом мейнтейнер-контента,
- `docs/_refactor-notes-<date>.md` с полным журналом операции.

## Сценарии применения

### Сценарий 1: green-field (нового README нет)

Пропустить Pass 0 (нет исходного материала). Запустить Pass 1, Pass 2
со всеми слотами как `<<HUMAN_NEEDED: ...>>`, кроме тех, что выводятся
из дочерних READMEs. Pass 3 пропустить (нечего разводить). Pass 4 —
прогнать. Результат: каркас для человека.

### Сценарий 2: refactor (существующий README перегружен)

Все 5 pass'ов по порядку. Главное — Pass 3 (сохранность).

### Сценарий 3: incremental update (мелкая правка лендинга)

Скилл **не применяется**. Точечные правки делаются вручную, без
переписывания. Скилл — для рефакторов и green-field.

## Definition of Done скилла

- Файл `README.md` существует, ≤ 120 строк, все лимиты выполнены.
- Файл `docs/get-started.md` существует, есть хотя бы один работающий путь.
- Все мейнтейнер-фрагменты разведены по `docs/architecture.md`,
  `docs/manifesto.md`, `docs/roadmap.md` с пометками `<!-- TBD: structure -->`.
- `docs/_refactor-notes-<date>.md` существует и содержит:
  - таблицу Inventory (Pass 0),
  - секцию `## Что нужно от человека` со всеми `<<HUMAN_NEEDED>>`,
  - блок Pass 4 — Verify с `[x]` всех 7 категорий чек-листа.
- Grep-проверка сохранности из Pass 3 вернула 0 строк `LOST:`.
- Grep-проверки антиконтента из Pass 4 вернули 0 утечек.
- PR открыт, описание включает summary из `_refactor-notes`.
